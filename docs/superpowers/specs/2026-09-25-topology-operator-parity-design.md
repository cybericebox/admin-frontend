# Топология задания: контракт с оператором и компактный редактор

**Дата:** 2026-09-25

**Статус:** утверждено пользователем

**Репозитории:** `admin-frontend` (`feature/base-redesign`), `AP Backend` (`feature/superadmin-infrastructure-read`), `laboratory` (`feature/lab-access-acl`). Работа идёт в текущих ветках; существующие незакоммиченные файлы не перезаписываются.

## 1. Цель и границы

Администратор должен настроить топологию варианта задания без расхождений между формой, API задания и фактическим запуском лаборатории. В поддерживаемом наборе устройств остаются контейнер, неуправляемый коммутатор и концентратор. Виртуальная машина удаляется как неподдерживаемый тип: сейчас оператор запускает её тем же контейнерным `Deployment`, а отдельных сохранённых VM-заданий нет. Упоминания VM в подсказках и ошибках соседней вкладки заменяются на «контейнер».

В этот срез входят: запросы и лимиты CPU/памяти контейнера, статические маршруты интерфейса, ограничение статического интерфейса одним IP-адресом, сквозной API-контракт, серверная проверка и компактная перестройка вкладки «Топологія». Уже работающие VPN/Internet, DHCP, типы интерфейсов, MAC, образ, профиль безопасности, переменные окружения, HTTP(S)-доступ, соединения, схема и тестовое развёртывание сохраняют поведение.

Не входят: несколько статических IP на интерфейс, ручное назначение подсетей VPN/Internet, чек-листы/тест-листы, новая логика VM, изменение фактических правил маршрутизации и новый экран мониторинга ресурсов. Последующее расширение до нескольких IP потребует изменения `AddrSpec.IP` оператора и конфигуратора, а не только формы.

## 2. Подтверждённое текущее состояние и подход

- `TopologySection` задаёт шлюзы, устройства и соединения; `DeviceCard` даёт вложенную навигацию и дополнительную рамку. Соседняя вкладка задач уже использует единый левый список и правую форму.
- API черновика хранит топологию в JSONB-снапшоте версии. Модель устройства и DTO не имеют `Resources`, модель IP и DTO не имеют `Routes`; перевод в `LabSpec` также их не передаёт. SQL-миграция не нужна, новые поля необязательны и старые снапшоты читаются с пустыми значениями.
- Оператор принимает `DeviceResources` (`cpuRequest`, `memoryRequest`, `cpuLimit`, `memoryLimit`) и статические `AddrSpec.Routes` (`dst`, `via`). Некорректные значения оператор может пропустить, поэтому авторская проверка должна происходить до развёртывания.
- Сейчас форма и API принимают несколько статических адресов, но перевод в `LabSpec` использует только первый. Новый контракт требует ровно один адрес при статическом режиме и ни одного при остальных режимах. Поскольку сохранённых VM-заданий нет, миграции таких устройств не требуется.

Выбран сквозной типизированный контракт, а не передача произвольного JSON оператора. Это сохраняет самостоятельную проверку на сервере и понятные ошибки в форме. Более узкий вариант (убрать VM и поправить IP, не проводя ресурсы и маршруты) не даёт администратору контролировать поддерживаемые оператором параметры. Передача сырого `LabSpec` расширила бы поверхность неподдерживаемых настроек и обошла доменные ограничения задания.

## 3. Данные и поведение

### Типы устройств

Допустимые новые значения типа: `container`, `unmanaged-switch`, `hub` во фронтенде, серверной доменной проверке и CRD оператора (исходные типы и оба набора сгенерированных CRD: `config/crd/bases` и `charts/laboratory/crds`). `vm` не предлагается в форме и отклоняется API. Коммутатор и концентратор по-прежнему не имеют образа, интерфейсов, переменных окружения, внешнего доступа, профиля безопасности и ресурсов контейнера. Привязка флага к устройству допускает только контейнер.

### Ресурсы контейнера

Необязательный объект `Resources` на устройстве содержит `CPURequest`, `MemoryRequest`, `CPULimit`, `MemoryLimit`. Пустое отдельное поле означает «не задано»; полностью пустой объект в API не отправляется. Формат значений соответствует Kubernetes Quantity (например, `250m`, `1`, `256Mi`). Сервер отклоняет синтаксически неверные, нулевые и отрицательные заданные значения; когда заданы запрос и лимит одного ресурса, запрос не может быть больше лимита. Фронтенд повторяет проверку для немедленной обратной связи, но сервер остаётся источником истины. При запуске значения без преобразования единиц попадают в `LabSpec.devices[].resources`; оператор применяет их к контейнеру.

### Адреса и маршруты

Статический интерфейс имеет ровно один адрес CIDR и необязательный шлюз; редактор показывает один ввод вместо списка и кнопки добавления адреса. API сохраняет существующее поле `Addresses []string` ради совместимости снапшота, но требует длину ровно 1 для `static`. Для `dhcp`, `dhcp-preset` и `none` список адресов, шлюз и маршруты пусты. Режимы и их текущее поведение не меняются.

У статического IP появляется необязательный список `Routes`, каждый элемент — `Dst` (CIDR назначения) и `Via` (IP следующего узла). Оба значения обязательны для добавленного маршрута, корректны по синтаксису и имеют одинаковую IP-семью. Сервер отвергает некорректный маршрут; оператор не должен получать запись, которую затем молча пропустит. При явном переключении интерфейса со `static` на другой режим форма очищает адрес, шлюз и маршруты. Перевод в `LabSpec` передаёт весь список маршрутов, не теряя записи.

### Дополнение пользователя: переменная флага

Привязка флага остаётся собственностью задачи (`LinkedDeviceID` + `DeviceFlagVar`), поскольку одно устройство может обслуживать несколько задач. В разделе переменных устройства редактор показывает вычисляемые строки «Прапор задачі → ИМЯ_ПЕРЕМЕННОЙ» со ссылкой на задачу, но не даёт редактировать их второй раз. Сервер и форма запрещают совпадение такой переменной с обычной переменной того же устройства и совпадение назначений двух задач на одну переменную устройства: иначе значение перезапишется. Тексты раздела передачи флага используют «прапор», а не «прапорець». Это дополнение сделано по прямому уточнению пользователя во время исполнения плана.

### Соединения и тестирование

Пары конечных точек (интерфейс устройства, VPN, Internet), ограничение одного соединения на шлюз, занятость интерфейса, схема и сохранение координат сохраняются. Тестовое развёртывание остаётся отдельным действием сохранённого варианта; чек-листы проверок не добавляются, поскольку такого контракта у оператора нет.

## 4. Компоновка вкладки «Топологія»

Основной путь автора: настроить сети в «Загальні» → добавить контейнеры в «Пристрої» → задать связи в «Зʼєднання» → проверить граф в «Схема». Четыре раздела стоят в одной вертикальной навигации слева, без дополнительной горизонтальной полоски. Устройства сгруппированы под «Пристрої»: там же список и действие добавления. Справа показывается только выбранный раздел; «Схема» не смешивается со списком «Зʼєднання». Выбранный пункт, наведение, клавиатурный фокус и действия удаления используют существующий ритм соседней вкладки; удаления не появляются второй раз в форме.

Левая колонка общая для всех разделов, справа остаётся одна панель настроек или графа. У `DeviceCard` убирается внутренняя рамка и третья вертикальная колонка. Его разделы «Основне», «Інтерфейси», «Змінні оточення», «Зовнішній доступ» становятся горизонтальными вкладками сверху правой панели. Это освобождает ширину полей и сохраняет выбранный раздел при переключении устройства, если он ему доступен. Для коммутатора/концентратора остаётся только «Основне».

В «Основне» сначала имя/тип и образ/профиль, затем компактная группа ресурсов без вложенной карточки: две строки CPU и память с колонками «Запит»/«Ліміт». В «Інтерфейси» существующий выбор интерфейса остаётся; у статического режима сначала один IP и шлюз, затем список маршрутов с локальной кнопкой добавления. Шлюзы показываются двумя лаконичными строками с включением и условным DHCP без отдельных вложенных карточек. «Зʼєднання» содержит только редактируемый список, а «Схема» — полноширинный граф тех же узлов и связей, с перетаскиванием узлов и сохранением координат. На схеме узлы читаются как сетевые устройства/шлюзы, порты и линии отделены, пересечения по возможности минимизированы; при необходимости выбрать пару для нового соединения это работает на схеме, но список соединений остаётся отдельным. Прикрепление схемы к заданию — возможное дальнейшее развитие, без нового поля/API сейчас.

На узких экранах левая навигация и правая форма следуют друг за другом; горизонтальные вкладки устройства переносятся или прокручиваются без обрезания подписей. Иконки помощи и ошибки остаются рядом со своими полями. Сокращение рамок и отступов не уменьшает кликабельные области, не скрывает обязательные подписи и не ломает порядок обхода клавиатурой. Палитра и типографика проекта не меняются.

## 5. Изменения по слоям и совместимость

1. **Оператор:** убрать `vm` из исходного `DeviceType`/валидационного enum и регенерировать CRD; формат ресурсов и маршрутов уже существует и не меняется. Удаление VM безопасно по подтверждению пользователя: старых VM-заданий нет.
2. **AP Backend:** дополнить доменные структуры топологии, DTO чтения/записи и `BuildLabSpec`; проверить значения при сохранении черновика и перед публикацией, как сейчас проверяется форма топологии. Новые поля необязательны, старые JSONB-версии остаются читаемыми. Нет нового маршрута API: расширяется текущий `PUT /api/exercises/:id/draft` и ответ версии.
3. **Admin frontend:** дополнить типы API, нормализацию, сериализацию, схему проверки и форму. Удалить VM из выбора, допустимых новых значений, подсказок и фильтра привязки флага в соседней вкладке. Позиция редактора и локальная копия черновика продолжают работать; новые не-секретные поля сохраняются вместе с топологией.

## 6. Ошибки, проверки и приёмка

- Неверный тип `vm`, ресурс, маршрут или второе статическое IP получают конкретную ошибку сервера. API не отбрасывает параметры молча и не отдаёт после сохранения неполный снапшот.
- Табличные Go-тесты покрывают ресурсы (пустые/частичные, корректные единицы, неверное значение, запрос больше лимита), маршруты (корректный IPv4/IPv6, неверный CIDR/IP, несовпадающая семья, запрет в не-статическом режиме), один статический IP, запрет VM и преобразование домен → DTO → домен → `LabSpec`. Операторские тесты подтверждают допустимый enum и применение ресурсов/маршрутов.
- Клиентские тесты покрывают отсутствие VM во всех выборах, поля ресурсов и маршрутов, ошибки возле поля, переключение режима IP и точную сериализацию. Полная проверка админки включает тесты, lint и сборку; сервер и оператор — свои Go-тесты и генерацию/сверку CRD.
- В браузере проверяются широкий, промежуточный и узкий экран, длинные имена устройств, несколько интерфейсов и маршрутов, пустые состояния, клавиатура и отсутствие лишней вложенной рамки. Не объявлять визуальную часть готовой только по прохождению тестов.
