# Адреса относительно подсетей VPN и Internet в топологии

**Дата:** 2026-09-25

**Статус:** согласованное направление; спецификация на проверке пользователя.

## Зачем это нужно

Подсеть VPN или Internet выделяется только при запуске конкретной лаборатории. Когда DHCP шлюза выключен, контейнер с обычным статическим адресом должен получить адрес из ещё неизвестной при редактировании подсети. Автору задания нужен тот же осмысленный выбор динамического сетевого значения, который уже есть во вставках описания задания, но в полях статического IP, шлюза и маршрутов. Сохранённая топология должна содержать ссылку на источник и номер хоста; перед созданием устройства оператор превращает ссылку в конкретные IP/CIDR данного запуска.

Подтверждённый выбор: VPN/Internet CIDR остаются автоматически выделяемыми для каждой лаборатории. Автор не вводит и не резервирует произвольный CIDR шлюза.

## Текущие инварианты

- Оператор выделяет VPN/Internet подсети `/24` и записывает их в `Lab.Status.VPN.CIDR` / `Lab.Status.Internet.CIDR` до материализации устройств. Интерфейс шлюза получает первый адрес подсети (`.1`).
- `static` сейчас хранит одну строку CIDR, необязательный строковый шлюз и маршруты `Dst` CIDR / `Via` IP; frontend, доменная модель, API DTO и LabSpec повторяют эту структуру.
- DHCP выдаёт адреса из хостов `.2–.254`. Относительный статический адрес из этого же диапазона конфликтует с DHCP, если DHCP источника включён.
- Вставки описания задания уже используют источники `vpn.subnet`, `internet.subnet` и IP источника с последним октетом. Новый UI повторяет их понятную модель выбора, но адрес в сетевом поле атомарен: вставка заменяет всё значение поля, а не часть текста.
- Схема топологии и API не опубликованы. Не вводить переходный парсер строковых токенов или миграцию старых топологий; обычные буквальные IP продолжают работать как раньше.

## Выбранное представление

Типизированные ссылки хранятся рядом с существующими буквальными значениями. В одном поле активен ровно один вариант — буквальный текст или ссылка; строка и ссылка одновременно запрещены.

```text
Network = "vpn" | "internet"
NetworkIPRef = { Network, Host }       // Host: 1..254; для адреса интерфейса 2..254
NetworkSubnetRef = { Network }         // вся выделенная /24 подсеть

IPConfig:
  Addresses: string[]                 // ровно один буквальный CIDR либо пусто при AddressRef
  AddressRef?: NetworkIPRef           // на интерфейсе преобразуется в host/24
  Gateway: string                     // буквальный IP либо пусто при GatewayRef
  GatewayRef?: NetworkIPRef           // .1 выбирается как «адрес шлюза»; другой хост — явно
  Routes: [{
    Dst: string                       // буквальный CIDR либо пусто при DstRef
    DstRef?: NetworkSubnetRef         // преобразуется в сетевой CIDR
    Via: string                       // буквальный IP либо пусто при ViaRef
    ViaRef?: NetworkIPRef             // .1 выбирается как «адрес шлюза»; другой хост — явно
  }]
```

В JSON API поля называются `AddressRef`, `GatewayRef`, `DstRef`, `ViaRef`; в доменном snapshot и LabSpec используются принятые в этих слоях регистры. Ссылки не являются произвольными шаблонами/выражениями и не допускают вычисления кода. Название узла в `VisualRender` на разрешение адресов не влияет.

## UI и поведение формы

- В блоке «Статична» у каждого применимого поля есть действие «Вставити значення»: выбор «Вручну» либо VPN/Internet. Для адреса интерфейса выбирается источник и номер хоста `.2–.254`; поле показывает, например, `VPN · хост .10 /24`, а не несуществующий пока IP.
- Для «Шлюз» доступны буквальный IP, «VPN-шлюз (.1)», «Інтернет-шлюз (.1)» и при необходимости иной номер хоста в выбранной подсети. Для `Dst` маршрута доступны буквальный CIDR, «VPN-підмережа» и «Інтернет-підмережа». Для `Via` — буквальный IP, адрес одного из шлюзов и иной номер хоста.
- Недоступные или выключенные VPN/Internet источники видны как недоступные с объяснением. Переключение на ручной ввод убирает ссылку; выбор ссылки очищает строку. Переключение интерфейса с `static` на `dhcp`, `dhcp-preset` или `none` очищает все четыре вида ссылок вместе с буквальными статическими значениями и маршрутами.
- Предпросмотр объясняет, что точные первые три октета неизвестны до запуска лаборатории. После запуска можно показывать разрешённый адрес из статуса/созданного устройства; отсутствие статуса не подменяется фиктивным CIDR.
- Лейблы, помощь, ошибки и выбор доступны с клавиатуры и имеют пары в украинском и английском каталогах. Текущие компактные поля панели и её изменяемая ширина сохраняются.

## Проверка и разрешение на сервере

- Frontend и backend проверяют одно значение на поле; статический интерфейс имеет ровно один буквальный CIDR **или** один `AddressRef`. Не-статический интерфейс не содержит ни буквальных значений, ни ссылок.
- Источник каждой ссылки должен быть включён в этой топологии. Для адреса интерфейса допустимы только хосты `2..254`; `.0` (сеть), `.1` (шлюз), `.255` (broadcast) запрещены. Для `GatewayRef`/`ViaRef` допустимы `1..254`. `DstRef` всегда обозначает весь `/24` сегмент.
- Если для выбранного источника DHCP включён, относительный статический адрес интерфейса запрещён, пока DHCP-пул не научится резервировать такие адреса. Ссылки на подсеть и адрес шлюза остаются допустимыми. Это предотвращает коллизию с текущим DHCP-пулом `.2–.254`.
- Несколько интерфейсов одного варианта не могут получить одинаковую пару `Network+Host` через `AddressRef`. Буквальные значения сохраняют текущую проверку синтаксиса; динамические ссылки IPv4 и буквальные IPv6 в одном маршруте не смешиваются.
- При публикации и тестовом запуске адрес интерфейса относительно VPN/Internet должен принадлежать L2-сегменту соответствующего шлюза (с учётом коммутаторов/хабов). Для незаконченного черновика отсутствие связи допустимо; для публикации — понятная ошибка с устройством и интерфейсом. Существующее правило оператора о несовместимых шлюзах в одном широковещательном домене остаётся.
- Backend переносит ссылки через DTO и LabSpec без преждевременной подстановки. Оператор после выделения `Lab.Status.*.CIDR`, но до создания `Device` CRD разрешает каждую ссылку в строковый CIDR/IP; неразрешённый источник или невалидный host переводит Lab в ошибку валидации, а не создаёт устройство с пустым IP. Материализованный `Device.Spec` и netconfig получают только буквальные адреса.
- Два запуска одного варианта используют один шаблон ссылок, но получают разные конкретные подсети. Строковые вручную введённые адреса и маршруты не переписываются.

## Проверка результата

1. Frontend: выбор/смена источника и хоста для каждого из четырёх полей, ручной ввод, очистка при смене IP-типа, валидация, нормализация и сериализация.
2. Backend: доменные тесты на допустимые и конфликтующие ссылки, DTO round-trip, передача в LabSpec и отказ публикации/тестового запуска при ошибках.
3. Оператор: `/24` разрешается из разных фактически выделенных CIDR, `.1` и `.10` дают ожидаемые значения; неверная ссылка отвергается до создания Device; буквальные адреса не меняются; проверка с выключенным DHCP.
4. Сквозной путь: сохранить версию → запустить тестовую лабораторию → увидеть конкретные IP/шлюз/маршрут в `Device.Spec` и netconfig. На текущей машине Kind-кластер отсутствует, поэтому e2e нельзя объявлять пройденным до появления тестового кластера; unit/controller проверки выполняются отдельно.

## Вне этого изменения

Ручная выдача CIDR шлюзам, изменение `/24`, резервирование статических хостов в активном DHCP-пуле, IPv6-относительные ссылки и произвольные выражения внутри IP-полей.
